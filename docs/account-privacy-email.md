# 회원 탈퇴와 커뮤니티 이메일 알림

## 범위와 기본값

이 변경은 기존 로그인 저장 방식을 변경하지 않습니다. 회원 탈퇴와 사이트 알림(새 답변·답변 채택)의 선택형 이메일 발송을 추가합니다. 이메일 알림은 기본적으로 꺼져 있고, 이메일 인증만 완료해도 자동으로 켜지지 않습니다. 실제 발송은 서버 설정을 켜야 시작됩니다.

## 회원 탈퇴

`DELETE /api/v1/auth/account`는 JWT, 현재 비밀번호와 `{ "currentPassword": "…", "confirmation": "회원 탈퇴" }`를 받습니다. 성공은 204이며, 관리자와 임시 비밀번호를 아직 변경하지 않은 계정은 거절합니다. 관리자는 다른 관리자에게 먼저 역할 해제를 요청해야 합니다.

한 트랜잭션에서 계정을 탈퇴 상태로 바꾸고 원래 이메일·사용자 이름·비밀번호를 무작위/비식별 값으로 대체합니다. 사용자 UUID는 유지합니다. 모든 Refresh token을 폐기하고 tokenVersion을 올려 기존 로그인·토큰 갱신·공개 프로필 접근을 차단하며 랭킹에서 제외합니다. 탈퇴 계정의 개인정보/권한을 되살리는 변경은 DB 트리거로도 거절합니다.

작성한 글·답변·문제·제출·기업 시험 기록은 익명 계정과 연결된 채 남습니다. **사용자가 본문·소스 등에 직접 쓴 개인정보는 자동 탐지/삭제하지 않습니다.** 탈퇴 전 직접 수정/삭제하거나 관리자와 상의해야 합니다. 저장글·팔로우·수신 알림·시험 초대의 기존 주소/사용자 ID는 제거합니다. 개인정보가 든 메일 작업·토큰·수신 옵션도 삭제합니다. 원래 이메일·이름으로 다시 가입해도 새 UUID이므로 과거 기록과 연결되지 않습니다.

Vibe 코딩의 대화·작성 파일·리비전과 기업 AI 시험의 평가 기록도 보존합니다. 현재 시험 담당자·관리자는 보존 답안과 리비전을 조회할 수 있으며, 탈퇴 응시자에 대한 새 평가는 409로 거절합니다. 응시자 본인의 접근은 기존 시험 참가 조건과 탈퇴 차단을 그대로 적용합니다.

탈퇴 전에 이미 인증을 통과해 시작된 다른 기능의 요청은 완료될 수 있습니다. 계정 변경/로그인/갱신은 사용자 잠금과 재검증으로 계정을 되살리지 못하게 합니다. 이미 발송된 메일이나 운영 백업·메일 공급자의 기록까지 회수하는 기능은 아닙니다. 별도 조직의 백업/개인정보 보관 정책을 적용해야 합니다.

로그아웃·기기 하나 로그아웃·다른 기기 모두 로그아웃도 토큰 갱신과 같은 사용자 행 잠금을 먼저 얻습니다. 회전 중 새로 만들어진 Refresh token이 로그아웃 UPDATE의 이전 DB 스냅샷 밖에 남는 경우를 막습니다.

## 이메일 API와 동의

| API | 기능 |
|---|---|
| `GET /api/v1/email/preferences` | `verified`, `answer`, `accepted`, `enabled` 조회 |
| `PATCH /api/v1/email/preferences` | `{answer:boolean,accepted:boolean}` 저장. 켜기는 발송 설정과 이메일 인증 필요 |
| `POST /api/v1/email/verification/request` | 로그인한 계정의 가입 이메일에 인증 요청 |
| `POST /api/v1/email/verification/confirm` | 같은 계정으로 로그인하여 `{token}`을 제출, 1시간·일회용 |
| `POST /api/v1/email/unsubscribe` | 로그인 없이 `{token}`으로 답변·채택 이메일 모두 끄기. 반복/만료/없는 토큰은 같은 일반 응답 |

새 수신 동의(`false→true`)만 인증·발송 설정을 요구합니다. 발송이 중단됐어도 기존 옵션 유지와 개별 해제는 가능합니다. 같은 로그인에서 자동으로 토큰이 갱신돼도 저장 전 선택은 보존하며, 같은 사용자라도 새 로그인으로 바뀌면 탈퇴 입력과 진행 중 요청을 분리합니다. 새 메일 링크로 이동하면 이전 요청을 취소하고 새 토큰을 사용합니다.

재발송하면 이전 인증 토큰과 대기 중인 인증 메일은 취소됩니다. 인증 메일은 주소별 60초 간격·24시간 5회 제한입니다. 탈퇴·재가입으로 제한을 초기화하지 못하도록 이메일의 HMAC만 저장하며, 마지막 요청에서 48시간이 지난 제한 기록은 청소합니다. 인증/수신 해제 토큰은 무작위 256비트로 만들고 DB에는 해시만 저장합니다. 토큰이 필요한 메일 내용은 별도 비밀키로 AES-GCM 암호화합니다.

링크는 `/email/verify#token=…`, `/email/unsubscribe#token=…`입니다. GET으로 변경하지 않고 사람이 확인 버튼을 눌러 POST합니다. 브라우저가 토큰을 읽으면 주소의 fragment를 제거합니다. 로그인 전 인증을 이어갈 때는 SPA history state에 링크를 전달하므로 모든 브라우저 기록에서 즉시 사라진다고 보장하지 않습니다. localStorage에 인증 링크를 저장하지 않습니다.

## 발송·실패·중복·경쟁 처리

사이트 알림과 같은 트랜잭션의 DB 트리거가 발송 원장(outbox)을 생성합니다. 수신 동의 이전 알림은 소급 발송하지 않고 본인 행동도 제외합니다. 글 제목/답변 전문/사용자 이름은 메일에 넣지 않으며 일반 안내와 해당 글 링크만 보냅니다.

워커는 발송 직전에 사용자 활성 상태·같은 이메일·인증·수신 옵션·동의 버전·원본 글/답변의 존재와 숨김·현재 채택 상태를 다시 확인합니다. 수신 해제 후 재동의해도 과거 동의로 생성된 작업은 발송하지 않습니다. 사용자→발송 작업 순서의 잠금으로 탈퇴/수신 거부와 발송을 직렬화합니다. 이미 시작된 최대 10초 발송 요청이 끝난 다음 탈퇴·수신 거부가 완료될 수 있으며, 공급자가 이미 접수한 메일은 회수할 수 없습니다.

한 계정의 커뮤니티 이메일은 시간당 최대 10건, 대기 100건, 전체 공급자 요청은 초당 최대 1건입니다. 초과 작업은 지연되고 오래된 작업은 폐기합니다. 같은 수신자의 동시 알림 삽입이 겹치거나 대기 상한에 도달하면 사이트 알림은 남고 이메일은 생략될 수 있습니다. 메일은 모든 사이트 알림을 무제한 복제하는 수단이 아닙니다.

외부 호출 전에 실제 공급자 요청 본문을 암호화하여 커밋하고 작업 ID 기반 idempotency key를 고정합니다. 타임아웃/429/5xx는 최대 8번, 최초 시도/생성에서 23시간 이내에만 재시도합니다. 공급자의 접수 후 DB 기록이 실패해도 같은 본문·키로 다시 요청합니다. 이는 [Resend의 24시간 idempotency 보관](https://resend.com/docs/dashboard/emails/idempotency-keys)을 이용하며, 외부 시스템까지 포함한 무조건적인 exactly-once 보장은 아닙니다. 결과가 불확실해도 보관 기간을 넘겨 새 키로 재발송하지 않습니다.

409 중 `concurrent_idempotent_requests`와 `resource_locked`도 같은 본문·키로 재시도합니다. `invalid_idempotent_request` 등 다른 409는 영구 실패로 처리합니다. 분류는 [Resend 공식 오류 문서](https://resend.com/docs/api-reference/errors)를 따르며 오류 본문은 최대 2,048바이트만 읽고 기록하지 않습니다.

인증 토큰은 만료 후 24시간이 지나면, 종료된 작업은 생성 후 30일이 지나면 워커가 제한된 배치로 청소합니다. 비밀키·주소·인증 링크·공급자 응답 본문은 로그에 남기지 않습니다. 종료/취소된 작업의 암호화 본문도 비웁니다.

## 서버 설정과 반영

현재 기본값 `EMAIL_ENABLED=false`에서는 발송하지 않으며 UI에도 미설정을 표시합니다. 실제 수신함까지 사용하려면 운영 담당자가 Resend 계정/검증된 발신 도메인과 다음 설정을 준비해야 합니다. 유료 서비스 가입/실제 메일 발송/배포는 이 로컬 작업에서 수행하지 않습니다.

```dotenv
EMAIL_ENABLED=true
EMAIL_WORKER_ENABLED=true
EMAIL_API_KEY=운영담당자가_설정
EMAIL_FROM=검증된발신주소
EMAIL_APP_ORIGIN=https://judge.yaki.kr
EMAIL_TOKEN_SECRET=JWT와_다른_32자_이상_전용난수비밀키
```

`EMAIL_APP_ORIGIN`은 경로·사용자 정보·쿼리·끝 슬래시 없는 HTTPS origin입니다. 키를 바꾸면 기존 암호화 대기 메일은 복호화할 수 없어 폐기되므로 안정적으로 보관합니다. 설정이 불완전한데 발송을 켜면 시작 시 거절합니다. 여러 API 프로세스에서도 DB 잠금으로 작업을 구분합니다.

배포 전 DB 백업 후 `AccountWithdrawal1795600000000`, `CommunityEmail1795600001000`을 적용하고 Front/Back을 함께 교체합니다. 적용되지 않은 구버전 API와 혼용하지 않습니다. 탈퇴 이력 또는 이메일 동의/발송/미만료 제한 기록이 있으면 schema down을 거절합니다. 데이터를 지우는 방식으로 롤백하지 마세요.

실제 발송 점검은 담당자가 소유한 테스트 주소로 인증 요청→인증→옵션 켜기→다른 계정의 답변→수신→수신 해제→후속 메일 없음→탈퇴 후 로그인/갱신 거절 순서로 수행합니다. 테스트에서는 실제 PostgreSQL과 모의 공급자 응답을 사용하며 실제 도메인 인증·외부 수신함·운영 서버 연결은 별도 확인이 필요합니다.

참고로 최신 main 통합 전 `117023c` 기반 전체 464개 실행에서는 460개 통과, 화면 로딩·순회 4개가 시간 초과했습니다. 당시 가용 메모리는 약 1GB였고 추적 기록에서 화면 모듈 초기화가 지연됐습니다. 같은 코드·기대값·제한 시간으로 실패한 4개만 worker 1개에서 다시 실행해 모두 통과했습니다. 메모리만이 원인이라고 단정하지 않으며, 이 과거 결과를 한 번에 전체 통과한 결과로 계산하지 않습니다.

별도로 초기 검증에서 확인한 테스트 환경 차이도 검증 의미를 유지하며 보완했습니다.

- Windows 클립보드가 읽기 시 LF를 CRLF로 변환했습니다. 앱이 실제 `writeText`에 전달하는 값은 줄바꿈까지 정확히 비교하고, OS에서 다시 읽는 값만 줄바꿈을 정규화합니다.
- 한 반응형 테스트에 5개 화면 폭 × 6개 페이지 탐색을 묶어 전체 30초 제한에 걸렸습니다. 추적 기록에서 앞선 화면은 정상 완료됐고 마지막 폭의 탐색 중 제한 시간이 끝났습니다. 폭별 5개 테스트로 나누고 페이지·가로 넘침 검사를 모두 유지했으며 에디터 포커스도 각 폭에서 확인합니다. 최종 전체 실행에서는 다섯 폭 모두 통과했습니다.

추가 정밀 검토에서 다음 결함을 수정했습니다.

- 갱신과 로그아웃이 겹치면 새 토큰이 살아남는 문제: 실제 PostgreSQL에서 세 로그아웃 경로의 실패를 먼저 재현하고 공통 사용자 잠금으로 수정했습니다. 갱신 선행·폐기 선행 6개 회귀를 포함해 탈퇴 통합 15개가 통과했습니다.
- 인증 요청의 고정 24시간 구간 경계에서 횟수를 초과하는 문제: 최근 요청 시각 배열을 잠금 안에서 집계하는 실제 최근 24시간 제한으로 변경했습니다.
- 일시적인 공급자 409를 영구 실패로 처리하는 문제: 알려진 일시 오류 두 종류만 동일 본문·키로 재시도합니다.
- 발송 중단 시 기존 옵션 유지·개별 해제가 막히는 문제: 신규 동의만 제한하고 감소는 허용합니다. 중단 직전 선택한 미저장 옵션도 다시 끌 수 있습니다.
- 자동 토큰 갱신 때 저장 전 선택이 초기화되는 문제, 같은 사용자 새 로그인에 이전 탈퇴 입력이 남는 문제, 새 메일 링크를 열어도 이전 토큰이 남는 문제: 로그인 identity별 폼 격리와 링크별 요청 수명주기로 수정했습니다.
- 최신 기업 Vibe 기능과 결합했을 때 탈퇴·초대 삭제로 담당자도 보존 답안을 조회할 수 없던 문제: 담당자 조회에 DB의 현재 소유자/관리자 권한을 검사하고 응시자 참가 검사와 분리했습니다. 실제 PostgreSQL에서 읽기·권한 위조·리비전·탈퇴 후 평가 거절을 검사했습니다.

메일은 수정 전 네 실패를 먼저 확인한 후 24개가 모두 통과했습니다. 프론트 핵심 세 실패도 수정 전에 재현했고, 수정 후 대상 57개와 마지막 보완 후 privacy 34개·빌드·타입 검사를 통과한 뒤 위 전체 검사를 수행했습니다. 검토와 회귀에는 수신 해제 후 재동의, 공급자 접수 후 DB 기록 실패의 동일 본문·키 재사용, 여러 탭·저장소 실패·늦은 응답도 포함합니다. 이는 명시한 범위의 검증 결과이며 모든 환경에서 무결함을 보장하는 의미는 아닙니다.

Firefox·WebKit, 실제 메일 공급자 및 수신함, 운영 서버 배포는 검증하지 않았습니다. Docker 엔진이 실행되지 않아 Redis·채점기 전체 파이프라인도 실행하지 않았습니다. 실제 PostgreSQL 통합 검사는 별도로 완료했고 테스트용 DB와 프론트 테스트 서버는 종료했습니다.
