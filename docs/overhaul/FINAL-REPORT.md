# UnsolvableOJ — 최종 엔지니어링 보고서

작성 기준: 2026-11-16 UTC. 실제 시작 기준선은 `6176015b63a1615cc2269172f246725ef08abab3`이다. 이 보고서는 이번에 확정한 변경 범위와 실제 증거를 기록하며, 플랫폼의 모든 실행 상태가 완전히 검증되었다고 주장하지 않는다.

## Executive Summary

보안·정확성·안정성·성능 관련 변경을 구현하고, 독립 리뷰와 해당 CI를 거쳐 `overhaul/integration`까지 통합했다. 기존 React/TypeScript/Vite, NestJS, PostgreSQL/TypeORM, Redis/BullMQ, go-judge 스택을 유지했다. `main`에는 직접 푸시하거나 병합하지 않았고 운영 서버·데이터·볼륨·Redis·실제 API 키를 사용하지 않았다.

최종 main 대상 PR: [integration→main 최종 PR 목록](https://github.com/yakisoba0728/UnsolvableOJ/pulls?q=is%3Apr+head%3Aoverhaul%2Fintegration+base%3Amain). 정확한 PR URL·최종 HEAD·완료한 CI는 [증거 PR #61](https://github.com/yakisoba0728/UnsolvableOJ/pull/61)의 최종 핸드오프에도 기록한다. 최종 통합 브랜치와 정확한 검증 HEAD/실행 결과는 해당 PR의 설명 및 Checks를 따른다. 소스 내용의 기준은 Back/src `2be5615a912a710c33b3feea3d6040143dd714dd`, Front/src `05948aee32bf0d620f75d5ff45fc3a73b39a96e2`이다. 커밋된 문서는 자기 자신의 이후 병합 SHA를 담을 수 없으므로 최종 GitHub PR 기록이 동적 검증 상태의 기준이다.

핵심 결과는 시험 제출 자격·마감 검증의 원자성, 이메일 초대의 인증 요건, 알림의 계정 격리·읽음 동시성, 제출 당시 문제 버전에 따른 진단 정보 제한, 실행 서비스 인증 확인, 출력 비교·DB 조회·결과 조립 비용 개선이다. 추가 검증에서는 실제 워커 종료/교체, 오래된 결과 차단, 단일 XP 반영과 Firefox 핵심 흐름을 확인했다. 각 결과의 실제 실행 상태는 아래와 TESTING.md에 기록한다.

## Architecture Changes

| 영역 | 변경 전 | 변경 후 |
|---|---|---|
| 기업 시험 제출 | 잠금 대기 전에 확인한 자격·상태가 이후 변할 수 있음 | 사용자 할당량과 시험 시도 잠금 뒤 현재 자격·실제 DB 시각을 확인하고 같은 트랜잭션에서 저장 |
| 워크스페이스 생성 | 트랜잭션 시작 시각으로 마감 평가 | 부모 시도 잠금 이후 `clock_timestamp()`로 평가 |
| 사용자 할당량 잠금 | FK 검사와 잠금 순환 가능 | `FOR NO KEY UPDATE`로 할당량 직렬화를 유지하면서 FK KEY SHARE 허용 |
| 알림 상태 | 로그인 소유권·GET·쓰기 완료 순서가 섞임 | 로그인 정체성별 상태와 요청 취소, GET epoch, 모든 쓰기 종료 후 서버 상태 재조회 |
| 진단 정보 저장 | 내부 callback의 표시에 의존 | 제출 당시 immutable 문제 버전으로 공개 범위·인덱스 검증 |
| 출력 비교 | 줄마다 Buffer 배열 생성 | 숫자 오프셋으로 비교하여 추가 메모리를 상수 수준으로 제한 |
| 기업 결과 조립 | 후보별로 전체 배열 반복 탐색 | 후보/과제별 Map 한 번 구성 |
| 통합 검증 | 일부 필수 검사·native 선택 누락 | 모든 필수 작업 연결, 실행 관련 변경과 최종 PR의 full 검증 강제 |

기술 스택 교체나 전체 재작성은 하지 않았다. 기존112개 API 경로·필드·언어·판정 enum을 제거하거나 변경하지 않았다. 의미상 호환성 변경은 인증된 이메일 초대, 임시 비밀번호 계정의 공개 가시성, 만료/종료된 시험의 거부, 내부 리디렉션 거부 및 인증 없는 실행 서비스 준비 실패다. [API-CHANGES.md](API-CHANGES.md)와 [DECISIONS.md](DECISIONS.md)에 구체적인 계약과 대안을 기록했다.

DB 변경은 사용자별 커뮤니티 조회를 위한 두 복합 인덱스의 추가뿐이다. 마이그레이션은26개가 되었고 테이블30개와 기존 컬럼·관계는 유지된다. 정방향·롤백을 실제 일회용 PostgreSQL로 검사했다. 운영 데이터의 파괴적 개편 권한을 사용하지 않았다.

## Functional Improvements

알림 패널에 로딩 실패 재시도와 읽음 실패 표시를 제공하고, 중복 페이지 요청·중복 행을 제거했다. 다른 계정으로 바뀌면 이전 내용과 늦은 응답이 남지 않는다. 개별 읽음과 전체 읽음이 겹치거나 패널을 다시 열어도 서버의 최종 읽음 상태를 재조회한다. 독립 리뷰가 초기 구현의 네 응답 순서 오류를 발견했고, 수정 후 일반 모드·StrictMode·실제 브라우저 회귀로 확인했다.

기업 시험은 종료·마감·초대 상태가 잠금 대기 중 변해도 잘못된 제출이나 새 워크스페이스를 만들지 않도록 강화했다. 초대 폼은 이메일 인증 요건과 사용자명 초대 방법을 설명한다. 결과 집계와 프로필 응답의 기존 순서·상태·점수 계약은 보존했다.

이번 신규 사용자 기능은 알림 복구 UX와 안내 개선으로 제한했다. 추가 대시보드·학습·에디터 기능을 구현했다고 주장하지 않으며, 범위 확장을 백로그로 남겼다.

## Security Improvements

이메일 초대는 기존 메일 인증 상태를 사용하고, 명시적인 사용자명 초대와 소유자·공개 시험 정책은 유지한다. 선택적 인증 경로에서는 비밀번호 변경이 필요한 계정에 익명 가시성을 적용한다. 자세한 채점 callback은 immutable 문제 버전으로 검증하고 비공개 진단을 저장하지 않으며, 기존 최소 callback과 유효한 부분 결과는 지원한다.

Judge 내부 요청은 리디렉션을 따르지 않는다. Judge와 Vibe 준비 검사는 인증된 요청의 성공 및 익명 요청의 거부를 모두 요구한다. Judge Docker 빌드 컨텍스트는 `.env.*`도 제외한다. 실제 비밀 유출이나 외부 공격 성공을 주장하는 변경은 아니다.

실제 PostgreSQL/HTTP 회귀와 native runtime 검증의 범위를 분리했다. privileged 샌드박스 컨테이너의 호스트 신뢰 경계, 커널 업데이트, 전용 실행 호스트, 자격 증명 관리 및 모든 프롬프트 공격에 대한 저항성은 이 수정만으로 해결되지 않는다. 공개 문서에는 운영 자격 증명이나 악용 절차를 넣지 않았다.

PR62의 정확한 HEAD `8801454dc297d0d1af0e195408767dcc002fe584`에서 [전체 CI43784688710](https://github.com/yakisoba0728/UnsolvableOJ/actions/runs/43784688710)의12개 작업이 모두 성공했고4개 이미지도 실제 빌드했다. 이 증거 문서 자체의 PR61 및 이후 main-PR 검증은 완료 후 각 PR 설명에 정확한 HEAD와 실행 링크를 남긴다.

첫 복구 CI는 Vitest hook에서 polling한 오류로 새 사례가 실행되지 않았고, 기존16개는 통과했다. 최초 워커 시작을 테스트 본문으로 옮겨 같은 단언·시간 제한을 유지했다. 실패 실행43784164298와 수정 후 결과를 숨기지 않고 기록했다. 보안 API의 빌드 동시 실행 실패, 로컬 브라우저 환경 차단, 독립 리뷰의 초기 알림/도구 결함도 TESTING.md에 기록했다. 실패를 무시하거나 테스트를 삭제·완화하지 않았다.

로컬 Docker/브라우저 실행 제약은 GitHub의 일회용 Linux/Docker/Playwright 환경으로 보완했다. 자연적인 DB lease60초 대기·Redis 재시작·API 재시작·모든 언어의 모든 실패 조합·장기 혼합 부하는 완료로 계산하지 않는다. [VALIDATION-COVERAGE.md](VALIDATION-COVERAGE.md)가 각 요구와 실제 단언을 연결한다.

## Outstanding Issues and readiness

요청한 전체 검증 목표 중 지속 혼합 부하, Redis/API 재시작과 장애 부하, 전용 실행 호스트 실증, native Vibe 실행 동등성, 실제 기기/전체 접근성, 운영 크기의 마이그레이션·오프호스트 복구, OS이미지·SBOM·라이선스 통지는 후속 작업이다. 기업 시험 전체 문제 버전 고정은 명시적인 정책·관계 설계가 필요한 별도과제로 남았다. 기존 제출은 각 제출 당시 버전을 사용한다.

확정된 P0/P1 수정과 변경별 리뷰/CI를 완료한 변경 묶음의 병합 준비 상태는 최종 PR의 정확한 HEAD full 검증으로 결정한다. 이 코드의 검증 성공을 운영 배포 준비 완료나 임의 규모 확장성 보증으로 해석하지 않는다. main 병합과 운영 배포는 수행하지 않는다. 세부 우선순위·수용 조건은 [BACKLOG.md](BACKLOG.md)에 있다.
