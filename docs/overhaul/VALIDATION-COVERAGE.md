## Infrastructure, observability and operational boundaries

`scripts/check-production-compose.mjs` runs `docker compose config` with generated test secrets. It asserts mandatory settings, no published production service ports, resource/PID/capability settings, private sandbox networking, matching service tokens, backup-container wiring, worker grace period/init and concurrency/memory-budget consistency. `scripts/check-sandbox-budget.mjs` checks the configured budget formula; its own output explicitly says host capacity still needs checking.

`scripts/check-compose.mjs --production` actually builds/starts the production service definitions with isolated overrides: unique project/network, generated credentials, RAM-backed test PostgreSQL/Redis data and dynamic loopback ports. It checks readiness and rejection of public access to internal Judge routes, runs the live Chromium flows, and removes only that project's resources. It does not deploy the production stack or validate the real Dokploy/TLS/CDN path.

The four Docker image jobs check buildability with `push: false`; they do not scan base images for vulnerabilities. Backup image/network/volume wiring is checked, but an off-host backup/restore exercise, RPO/RTO, storage exhaustion, persistent-volume recovery, resource-pressure soak and actual alert delivery are not established. Worker presence/health-file assertions do not measure alerting coverage or time to recovery. Privileged native sandbox operation remains a host-isolation/deployment consideration, not something eliminated by these passing tests.

## Performance and stress boundaries

Use [PERFORMANCE.md](PERFORMANCE.md) and the committed benchmark JSON for numerical before/after conclusions. The suites below are scoped measurements; their results cannot be extrapolated to platform capacity.

| Measurement | Source and bounded experiment | What it cannot establish |
|---|---|---|
| Frontend bundle | Vite production output from `npm run build --prefix Front`; changed telemetry loading verified by its privacy/lazy-load assertions | Real-browser navigation timing, Core Web Vitals, slow-device rendering, editor responsiveness or network-cache effectiveness. |
| Judge output comparison | `Judge/scripts/benchmark-output.mjs`, `Judge/benchmarks/output-comparison.json`; fixed baseline comparator; ordinary, blank, dense and long-line fixtures; five fresh-process samples per mode with alternating order; CPU/RSS recorded | Compiler time, native sandbox overhead, jobs/second, mixed-language throughput or queue wait. |
| Enterprise score assembly | `Back/scripts/benchmark-enterprise-scores.mjs`, `Back/benchmarks/enterprise-scores.json`; fixed synthetic sizes, alternating fresh-process samples and complete-output digest equality | SQL, HTTP, serialization cost or enterprise request throughput. |
| Community profile indexes | `Back/scripts/benchmark-community-indexes.mjs`, `Back/benchmarks/community-indexes.json`; exact saved/voted service SQL, synthetic 10,000 users/2,000 posts/200,000 saved rows/200,000 vote rows; single-connection warmed EXPLAIN ANALYZE/BUFFERS samples; response row/order digest equality | Concurrent writers, index maintenance cost under sustained writes, whole-database workload, vacuum behavior or HTTP throughput. |
| HTTP listing benchmark | `Back/scripts/benchmark-http.mjs`; synthetic 2,000-problem database; separate loopback API child; concurrency 1/8/32, three 80-request rounds each, 20 warm-up requests; separate 160-request rate-limit burst | Sustained saturation, a soak test, failure recovery under load, multi-instance scalability, representative authenticated/mixed traffic, or Judge throughput. It is 900 bounded requests including warm-up and rate-limit validation. |

The HTTP harness measures request latency percentiles, observed HTTP throughput/status counts and API-child CPU ticks. Its RSS is the API process's lifetime high-water mark, not an allocation delta per round. API CPU excludes the client, PostgreSQL and Redis. Expected responses are asserted: each measured 80-request round succeeds; the isolated 160-request burst yields 100 successful responses and 60 HTTP 429 responses. This checks configured rate-limit behavior, not maximum sustainable capacity. Clearing owned throttle counters between rounds is part of the experiment and must be disclosed when interpreting its results.
